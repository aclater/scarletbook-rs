# Contributing and the clean room

[![Fuzzing](https://github.com/aclater/scarletbook-rs/actions/workflows/fuzz-long.yml/badge.svg?branch=main)](https://github.com/aclater/scarletbook-rs/actions/workflows/fuzz-long.yml)

scarletbook is a clean-room implementation: it is written only from the specifications and
conformance corpus of [aclater/sacd-spec](https://github.com/aclater/sacd-spec). Before
contributing, read [CONTRIBUTING.md](../CONTRIBUTING.md), which explains the clean-room rule.
The clean-room record is in [CLEANROOM.md](../CLEANROOM.md), and vulnerabilities are reported
as described in [SECURITY.md](../SECURITY.md). Changes are listed in
[CHANGELOG.md](../CHANGELOG.md); how a release is made is in [RELEASING.md](../RELEASING.md).

## Layout

| Path | Content |
|---|---|
| `crates/scarletbook` | the library (`#![deny(unsafe_code)]`, with one run-time dispatch module as the exception; no I/O beyond the reader it is given) |
| `crates/scarletbook-pcm` | DSD64 to 24-bit PCM conversion (88.2, 176.4 and 352.8 kHz), deterministic per frame; independent of the reader; deprecation planned ([#398](https://github.com/aclater/scarletbook-rs/issues/398)); no new features; see its [README](../crates/scarletbook-pcm/README.md) |
| `crates/scarletbook-ffi` | the C ABI (`include/scarletbook.h`, generated by cbindgen; `libscarletbook_ffi.{a,so,dylib}`, `scarletbook_ffi.dll`); see the [C ABI guide](c-abi.md) |
| `crates/scarletbook-bench` | `bench`, the benchmark program of sacd-spec `benchmarks/README.md` |
| `crates/scarletbook-conformance` | the corpus runner and `scarletbook-toc`, which prints a TOC as manifest-shaped JSON |
| `corpus/` | the sacd-spec conformance corpus, copied unchanged (CC0-1.0) |
| `fuzz/` | cargo-fuzz targets, seeded from the corpus |

```sh
cargo test --workspace                      # includes every corpus case
cargo run -p scarletbook-conformance --bin scarletbook-toc -- corpus/images/hostile-base.iso
```

## Changing the C ABI

The header, `crates/scarletbook-ffi/include/scarletbook.h`, is generated: regenerate it with
`cbindgen --config cbindgen.toml --crate scarletbook-ffi --output include/scarletbook.h`
in `crates/scarletbook-ffi` (cbindgen 0.29.4; CI checks the committed header). What counts as
an addition and what as a breaking change is in
[ABI compatibility](c-abi.md#abi-compatibility).

CI enforces this. `crates/scarletbook-ffi/abi/abi-N.txt` is the baseline of ABI version N:
the header's declarations without comments or layout. `.github/scripts/abi-check.py`
compares the header with the baseline of its `SB_ABI_VERSION` and says which case applies:

- a pure addition fails with "additive change: regenerate the baseline with --write". Run
  `python3 .github/scripts/abi-check.py --write` in the same commit, so the baseline always
  matches the header on `main`;
- anything else fails with "breaking change: bump SB_ABI_VERSION and add abi-(N+1).txt".
  Increment `SB_ABI_VERSION` in `crates/scarletbook-ffi/src/lib.rs`, regenerate the header
  with cbindgen (as above; editing the header alone fails CI's `--verify`), run `--write`
  to add the new baseline, and add a row to the table in [ABI compatibility](c-abi.md#abi-compatibility).

On a pull request, CI also classifies the header against the base branch's baseline of the
same version, so rewriting the baseline by hand does not hide a breaking change, and fails
if a baseline of an earlier version is edited, moved or removed.
`.github/scripts/abi-check-test.py` tests the check. A behaviour change that leaves the
declarations alone is invisible to it: bump `SB_ABI_VERSION` in `src/lib.rs` by hand,
regenerate the header (it then differs only in that line) and run `--write`.
